# Milestone 01 Database Schema Plan

This plan captures the Phase 2 review of the eight entities named in
`IMPLEMENTATION_PLAN.md`. Phase 2 creates only these minimum Milestone 01
tables. It does not implement gameplay operations, services, or future-game
tables.

## Shared conventions

- Use UUID primary keys generated by the application for player-owned rows.
- Use timezone-aware UTC timestamps (`created_at`, and `updated_at` on mutable
  records). Keep game time separate from wall-clock timestamps.
- Reference player state through `game_save_id`; use foreign keys and explicit
  delete behavior. Prefer `RESTRICT` for referenced history and `CASCADE` only
  for owned state that is deliberately deleted with a save.
- Store money as `NUMERIC(14, 2)` in USD. Never use floating-point types for
  monetary values. Company balance must be nonnegative.
- Store Milestone 01 quantities as integers. Balances and reserved quantities
  must be nonnegative, and reserved quantity must not exceed on-hand quantity.
- Store global content references as stable string IDs; catalog definitions
  remain in version-controlled `game-data/` rather than being copied into
  player rows.
- Add indexes to foreign keys and commonly queried save/status/time columns.

## Planned entities

| Table | Key relationships and uniqueness | Phase 01 field scope and constraints |
|---|---|---|
| `companies` | UUID PK; referenced by saves | `name` (maximum 40 characters), nonnegative `cash_balance NUMERIC(14,2)`, timestamps. Name validation remains a later service concern. |
| `game_saves` | UUID PK; FK to company; company has a one-to-many relationship to saves | Naive game-clock `game_time`, `content_version`, timestamps. No unique company constraint, so multiple saves remain possible. |
| `facilities` | UUID PK; FK to save; unique `(id, game_save_id)` target for save-consistent child FKs | Stable facility definition ID and timestamps. |
| `equipment_instances` | UUID PK; FK to save; optional composite FK to facility in the same save | Stable equipment definition ID and timestamps; no catalog copy or equipment behavior. |
| `inventory_balances` | UUID PK; FK to save and same-save facility; unique `(game_save_id, facility_id, item_id)` | Stable item ID, integer `quantity`, integer `reserved_quantity`; both nonnegative and reserved no greater than on-hand quantity. |
| `production_orders` | UUID PK; FK to save and same-save facility | Stable recipe ID, positive integer batch count, status, naive game-clock start/due/completion fields, timestamps. No queue processing in this phase. |
| `inventory_movements` | UUID PK; FK to save and same-save facility | Stable item ID, nonzero signed integer quantity delta, movement type/reference, creation timestamp; records are append-only by convention. |
| `financial_transactions` | UUID PK; FK to save | Transaction type/reference, nonzero signed `NUMERIC(14,2)` amount, currency `USD`, description, creation timestamp. Positive amounts are credits and negative amounts are debits. |

## Migration boundary

The first revision establishes the Alembic baseline. The next revision
creates these eight tables and only their Milestone 01 fields. No company,
save, inventory, purchasing, manufacturing, or financial operations are
implemented in Phase 2. Database constraints complement service validation;
they do not replace it.
